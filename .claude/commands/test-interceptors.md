# /test-interceptors — does the card actually Do The Thing

The depths trap: a card's text says "deal 3 damage when this enters",
its `setup_interceptors` registers an ETB trigger, the trigger fires —
and the `effect_fn` returns `[]` because the engine didn't yet support
damage events at the time the card was wired. Downstream stages (deck
tournaments, AI tuning) waste hours producing "the deck is bad" results
that are really "the engine is broken". This skill catches that class
of bug *before* downstream stages run.

CLAUDE.md notes the existing scale of this issue: across the 12 real
MTG sets, ~736 of ~2,486 wired cards have an interceptor that fires
but does nothing (`effect_fn = return []` pending engine support), and
another ~604 are bare `return []` stubs. Card sets generated by
`/new-set` and `/new-game` are vulnerable to the same failure mode if
the subagent overran a hook the engine doesn't expose.

## Arguments

User invoked with: `$ARGUMENTS`

Optional (inferred from repo state if absent — see "Game inference" below):
- `--game <name>` — engine to test. Maps to `src/cards/<name>/`.

Other optional:
- `--set <code>` — restrict to one set (e.g. `MC1`, `WOE`). Default: all
  cards in `src/cards/<name>/`.
- `--out tests/test_<game>_interceptors.py` — generated test file path.
- `--fail-on-empty` — if set, treat "interceptor fires but emits 0
  events" as a hard failure. Default: warn-only (some legitimate
  interceptors no-op when conditions aren't met, e.g. "draw a card if
  graveyard is empty").

## Workflow

### Game inference (when `--game` is omitted)

If `--game <name>` is not provided, infer it from repo state:

1. Run `git status --short`. Tally how many modified/untracked files
   match `src/cards/<X>/`, `src/engine/<X>*.py`, `src/ai/<X>_adapter.py`,
   `frontend/src/games/<X>.tsx`, or `docs/strategy/<X>.md` for each
   candidate `<X>`.
2. If a single game has ≥3 matches AND dominates runners-up ≥3:1, pick it.
3. Else: run `git log -5 --name-only` and apply the same tally to
   recent commits.
4. Else: list `src/cards/*/__init__.py`. If only one engine directory
   exists, use it.
5. Else: halt with "Could not infer --game. Candidates: <list>. Pass
   --game explicitly."

Print the inferred game in the discovery block so it's visible.

### 0. Pre-flight discovery

Run before spawning the subagent:

1. Confirm `src/cards/<game>/` exists. Halt if not.
2. Identify the engine's trigger conventions by reading 2–3 existing
   card source files (e.g. `src/cards/<game>/<set>.py`). Different
   engines use different shapes — examples:
   - **MTG-style**: `setup_interceptors=fn` returning interceptors via
     `make_etb_trigger`, `make_death_trigger`, etc.
   - **Minecraft**: `on_play=`, `on_attack=`, `on_block=` direct
     callbacks on the card factory.
   - **Hearthstone**: `battlecry=`, `deathrattle=`, plus
     `setup_interceptors=` for passives.
   - **Pokemon/YGO**: per-engine helpers in their respective adapters.
   Note the conventions in your discovery summary so the subagent
   knows what to grep for.
3. Find an existing test file for the engine (e.g.
   `tests/test_<game>.py`, `tests/test_lorwyn.py`,
   `tests/hearthstone/test_*.py`). The subagent will mirror its
   "create object → fire trigger → assert" scaffolding.
4. Find the test runner. Most engines run via `python tests/test_X.py`
   directly (per CLAUDE.md note "Pokemon/YGO tests run directly, not
   via pytest"); some run via pytest. Confirm which.

Print a discovery summary:

```
=== /test-interceptors pre-flight ===
game:           <game>
card pool:      <DICT_NAME> at src/cards/<game>/__init__.py  (<N> cards)
trigger style:  <e.g. "setup_interceptors + make_etb_trigger" or "on_play callback">
test scaffold:  tests/<existing_test>.py
runner:         python tests/<file>.py  (or pytest, etc.)
==> spawning test-generator subagent...
```

### 1. Spawn test-generator subagent

Use `Agent` tool with `subagent_type=general-purpose`. Brief:

> You are the interceptor-verification test generator for the `<game>`
> engine. Your job: produce a single test file at `<OUT_PATH>` that
> validates every card with a trigger or active interceptor actually
> emits the effect its rules text claims.
>
> **Read first** (in this order):
>   1. The card source files under `src/cards/<game>/` (filter to
>      `--set <code>` if specified). Build an in-memory list of
>      `(card_name, trigger_kind, expected_effect_keywords)` for every
>      card with a non-trivial interceptor. `trigger_kind` is the
>      helper used (e.g. `make_etb_trigger`, `make_death_trigger`,
>      `on_play`, `battlecry`). `expected_effect_keywords` come from
>      parsing the card's `text` field — e.g. "draw a card" → `DRAW`,
>      "gain N life" → `LIFE_CHANGE`, "deal N damage" → `DAMAGE`,
>      "destroy target" → `OBJECT_DESTROYED`, "create N tokens" →
>      `TOKEN_CREATE`.
>   2. The existing test scaffolding at `<TEST_SCAFFOLD_PATH>`. Mirror
>      its setup helpers (e.g. `create_creature_on_battlefield`).
>      Don't reinvent the wheel — reuse helpers if they exist; copy
>      them into the new test file if they're nested.
>   3. `src/engine/types.py` for the EventType enum so you know which
>      event constants to assert against.
>
> **Generate one test per card.** Each test:
>   1. Builds a minimal game state (1–2 players, hand/library populated
>      enough that the trigger has a target if needed).
>   2. Drops the card into the right zone for its trigger:
>      - ETB / battlecry / on_play → battlefield (via the engine's
>        canonical entry path; usually a ZONE_CHANGE event).
>      - Death / deathrattle → battlefield, then destroy.
>      - Attack triggers → battlefield, then declare attacker.
>      - Activated abilities → battlefield, then activate.
>      - Static effects → battlefield, then check a relevant query.
>   3. Captures emitted events (use the engine's event log /
>      `game.events` / equivalent — discover from existing tests).
>   4. Asserts at least one event in the log has a `type` matching one
>      of the expected effect keywords. If the card text mentions
>      multiple effects, assert one is present (not all — some are
>      conditional).
>
> **Cards you cannot auto-test**: modal cards (multiple choice
> effects), cards requiring target choice from a non-trivial pool,
> cards whose effect depends on opponent's state, equipment statics
> that need an attached creature, sagas, replacement effects. Skip
> these and add them to a `SKIPPED_CARDS = {...}` dict at the top of
> the test file with a one-line reason for each. Do not silently
> exclude them — the user needs to see what wasn't covered.
>
> **File structure** (`<OUT_PATH>`):
>
> ```python
> """Auto-generated interceptor verification for <game>. See /test-interceptors."""
>
> import sys
> sys.path.insert(0, '/path/to/repo')
>
> from src.engine import Game, Event, EventType, ZoneType
> from src.cards.<game> import <DICT_NAME>
>
> SKIPPED_CARDS = {
>     "Card Name 1": "modal — needs human selection of mode",
>     ...
> }
>
> # ... reused/copied scaffolding helpers ...
>
> def test_card_<snake_name>():
>     """<card name>: expects <expected effect>"""
>     # ... setup, trigger, assert ...
>
> # ... one per card ...
>
> if __name__ == "__main__":
>     # Run every test, count pass / fail / skipped, print a summary table.
>     import traceback
>     tests = [v for k, v in globals().items() if k.startswith("test_")]
>     passed, failed, errors = [], [], []
>     for t in tests:
>         try:
>             t()
>             passed.append(t.__name__)
>         except AssertionError as e:
>             failed.append((t.__name__, str(e)))
>         except Exception as e:
>             errors.append((t.__name__, f"{type(e).__name__}: {e}"))
>     print(f"\n=== Interceptor verification: <game> ===")
>     print(f"  passed: {len(passed)}")
>     print(f"  failed: {len(failed)}")
>     print(f"  errors: {len(errors)}")
>     print(f"  skipped: {len(SKIPPED_CARDS)} (see SKIPPED_CARDS)")
>     if failed:
>         print("\n--- FAILURES ---")
>         for name, msg in failed[:20]:
>             print(f"  {name}: {msg}")
>     if errors:
>         print("\n--- ERRORS ---")
>         for name, msg in errors[:20]:
>             print(f"  {name}: {msg}")
>     sys.exit(0 if not failed and not errors else 1)
> ```
>
> Use `Write` for the file. Then print a one-paragraph summary: how
> many tests were generated, how many cards skipped, which trigger
> kinds dominate.

### 2. Run the generated tests

```
PYTHONPATH=. python <OUT_PATH>
```

Capture stdout/stderr. Parse the summary line for pass / fail / error
counts.

### 3. Triage

For each failure:
1. Read the failing test and the card def it targets.
2. Categorize:
   - **Empty effect** — interceptor fires but produces no events. The
     card is wired but the engine doesn't support its effect, OR the
     `effect_fn` was stubbed out and never filled in. This is the
     core depths case.
   - **Wrong effect** — interceptor produces events but not the type
     the rules text implies. E.g. "draw a card" emitted `LIFE_CHANGE`.
     Likely a copy-paste bug in the card def.
   - **Trigger never fires** — the canonical event was emitted but no
     interceptor ran. The card's `setup_interceptors` may not have
     registered, or registered against the wrong event type.
   - **Test scaffolding bug** — the test itself is wrong (e.g. didn't
     put the card in the right zone). Fix the test, not the card.
   - **Engine bug** — the trigger fires but a downstream handler
     crashes. Fix the handler.
3. For empty-effect failures specifically: do NOT silently mark the
   card "tested ok with empty effect". Either fix the engine to
   support the effect, fix the card to emit the right events, or add
   the card to `SKIPPED_CARDS` with a reason like "engine does not yet
   support replacement effects — see engine_gaps.md".

### 4. Report

Tight markdown:

1. **Tests generated**: N (out of M cards in scope; X skipped)
2. **Pass / fail / error**: counts, with fail rate %
3. **Top failure categories**: ranked
4. **Recommended next moves**: which engine gaps to fill, which cards
   to fix, which categories deserve a wholesale rewrite

If invoked from `/new-game-plus` P0, this report is the gate: a high
fail rate means the polish pass should pause and fix the engine before
running the deckbuilder + AI tuner. The orchestrator decides
threshold; a sensible default is "pause if pass rate <70% on a
freshly-generated set."

## Notes

- Generated tests are auto-regenerable. If the card pool changes, run
  the skill again — it overwrites `<OUT_PATH>`. Don't hand-edit the
  generated file; if a test is wrong, fix the generator's heuristics.
- The test file is checked into the repo (it's real test coverage, not
  ephemeral). Subsequent edits to cards should keep it passing.
- The skipped-cards list is the human's punch list. Auto-testing
  modal / target-choice cards is possible but the heuristic complexity
  isn't worth it — better to test those manually or via a focused
  capability_test.py run.
